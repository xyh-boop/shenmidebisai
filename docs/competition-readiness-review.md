# AegisFlow 参加“Agent+”攻防挑战赛的修改意见

## 结论

**AegisFlow 可以作为参赛作品的技术原型，但当前状态不宜宣称“完全符合”赛事要求，也不应直接作为最终提交版本。**

项目与“AI 攻防全链路构建与实践落地”主题存在明确交集：它提供从安全读取、静态候选发现、Source-to-Sink 证据构建、风险路由、可选模型复核到 JSON/HTML 报告和基准评测的自动化流程。然而，赛事还要求可比的量化实验、脱敏实践案例、规范化技术方案，以及可在指定靶场运行的已提交 Agent。后四项尚缺少可审查的交付证据。

## 已具备且应保留的能力

1. **可落地的源码审计原型**：支持 Python 与 JavaScript/TypeScript，覆盖命令注入、SQL 注入、路径遍历和不安全反序列化四类高风险问题。
2. **可审计的自动化链路**：扫描流程由安全读取、语法分析、证据图、置信度与成本路由、可选复核和报告组成；结果具有稳定标识和可追溯证据。
3. **明确的安全与成本控制**：默认离线，不执行目标代码；Agent 模式有上下文裁剪、脱敏、请求数/令牌/费用预算及失败降级机制。
4. **可复现实验的基础**：项目内置独立真值清单和 benchmark 命令，产物可计算 precision、recall、F1、误报率等指标。

这些能力应成为技术方案和演示的主线，而不是把项目描述成“通用自主攻防 Agent”。当前实现更准确的定位是：**以确定性静态分析为主、以受约束模型复核为辅的本地源码安全审计 Agent。**

## 不应夸大的结论

以下边界应在报名材料、演示视频和答辩中明确写出：

- 不支持二进制漏洞自动化分析。
- 不承诺跨文件、跨过程或全程序污点分析。
- 不进行动态执行、运行时可利用性判断、主动利用或自动修复。
- 当前规则仅覆盖四类 CWE，不代表通用漏洞检测能力。
- 内置 benchmark 的 `precision=1.0`、`recall=1.0` 和 `F1=1.0` 仅适用于 16 个内置样例及其既定配置，不能外推为真实代码库、SRC 或靶场的通用效果。
- Verifier、Critic、Arbiter 是受固定输入/输出契约约束的复核阶段，而不是可自行规划和执行攻击行动的自由 Agent。

上述表述既是技术诚实要求，也能避免评审将项目与二进制分析、自动化利用或通用漏洞挖掘能力进行错误比较。

## 必须补齐的交付物

### P0：参赛合规与可验收性

1. **确认赛事时效与靶场契约**
   - 文章所述线上挑战窗口是 8 月 16 日 10:00 开放 24 小时、8 月 17 日 10:00 开始计分。应先在 BSRC 官方活动页确认适用年份、报名状态、靶场输入输出协议、运行环境、资源限制和网络策略。
   - 在未完成真实靶场试跑前，不得写“支持赛事靶场”或“具备闯关能力”。

2. **准备独立提交包**
   - 个人/团队介绍：团队不超过 3 人，明确研发、评测、演示/交付分工。
   - Demo：提供固定版本、固定命令、固定输入和预期输出；避免演示时依赖未记录的本地状态。
   - 技术方案：单独整理为不超过 5,000 字的 Markdown 或 PDF，不能仅以现有零散文档替代。
   - README：补充操作系统、Python 版本、依赖安装、模型配置、离线运行、Agent 模式、复现实验、故障排查和安全声明。

3. **提供脱敏实践案例**
   - 至少选取 1 个有授权的真实代码审计案例，或构造与真实业务结构相近的脱敏案例。
   - 案例应包含：问题背景、授权/脱敏说明、目标文件规模、漏洞来源到危险汇点的证据、人工验证结论、修复建议、扫描耗时和复现步骤。
   - 不提交未授权的真实漏洞细节、凭据、内部地址、完整业务源码或可直接利用的攻击载荷。

### P1：量化评测与技术说服力

4. **建立“传统模式 vs AegisFlow”对照实验**

   赛事要求的指标不能只在内置样例上报告。建议将同一批、未参与规则调优的脱敏样本作为测试集，并固定版本、硬件、超参数和人工验证标准。

   | 指标 | 建议口径 | 最低交付证据 |
   |---|---|---|
   | 漏洞发现率 | `TP / (TP + FN)`，按人工确认的漏洞计 | 真值清单、匹配规则、FN 清单 |
   | 误报率 | `FP / (TP + FP)`；如用其他定义，必须注明 | FP 清单和人工复核记录 |
   | 代码审计量级 | 文件数、有效代码行数、语言分布 | 输入清单与过滤规则 |
   | 单高危漏洞发现时长 | 从扫描启动到首条经规则定义为高危的发现 | 原始时间戳和运行日志 |
   | 大模型运行成本 | 请求数、输入/输出 token、模型单价、实际或估算成本 | 模型配置与费用计算公式 |
   | 人机验证时间比例 | 人工复核时间 / 总审计时间 | 计时表与复核人记录 |

   对照组应至少包含“纯人工审计”或“既有规则扫描流程”之一。任何结论都要注明样本规模、样本来源、统计周期和置信限制，不使用“零误报”“全覆盖”“自动发现全部漏洞”等绝对化表述。

5. **把 Agent 增益单独验证**
   - 分别运行 `offline` 与 `agent` 模式，报告两者的 TP、FP、FN、人工复核量、耗时和成本。
   - 记录模型超时、无效响应、预算耗尽时产生的 `needs_review` 数量，证明失败不会被静默确认。
   - 不将模型复核结果与离线基准结果混为同一条“准确率”结论。

### P2：演示与表达

6. **制作五分钟以内的可验证演示**
   - 0:00-0:30：说明问题、目标代码规模和授权/脱敏边界。
   - 0:30-2:00：执行离线扫描，展示来源、传播、约束和危险汇点证据。
   - 2:00-3:00：展示人工确认、误报抑制或安全反例。
   - 3:00-4:00：展示 benchmark 指标及其样本限制。
   - 4:00-5:00：展示 Agent 模式的预算、脱敏、失败降级与成本记录；最后重申能力边界。

7. **把创新点表述为可验证主张**

   推荐表述：

   > AegisFlow 以本地确定性证据图建立可复现基线，仅将高风险且证据存在歧义的候选交给受预算和结构化契约约束的模型复核，从而在可审计性、模型调用成本和人工复核负担之间建立可量化权衡。

   该表述与现有实现一致，也便于用 P1 的对照实验验证。

## 推荐的提交材料结构

1. 项目摘要：问题、适用范围和明确边界。
2. 技术架构：安全读取 -> AST/Tree-sitter -> 证据图 -> 路由 -> 受约束复核 -> 报告与 benchmark。
3. 核心方法：四类规则、证据节点、复核协议、成本与失败控制。
4. 实践案例：脱敏样本、发现证据、人工验证、修复建议。
5. 实验设计：数据集、真值、对照组、指标定义、运行环境。
6. 实验结果：原始表格、图表和统计限制。
7. 靶场适配：已验证的运行接口、资源上限和试跑结果；未验证前必须标注为待验证。
8. 创新点与限制：只陈述由实现或实验支撑的结论。

## 验收门槛

在以下事项完成前，建议将项目状态标为“参赛原型完善中”，而不是“可直接提交”：

- [ ] 官方赛事页面和靶场运行协议已确认。
- [ ] 已完成至少一次真实靶场或等价模拟环境试跑。
- [ ] 已提供至少一个授权且脱敏的实践案例。
- [ ] 已完成独立测试集上的传统流程与 offline/agent 模式对照实验。
- [ ] 已保存原始日志、真值、人工复核记录和成本计算依据。
- [ ] 已完成 5,000 字以内技术方案和可复现 README。
- [ ] 已录制或部署可复核的演示材料。
